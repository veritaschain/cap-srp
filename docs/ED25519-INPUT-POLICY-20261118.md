# Ed25519 backend selection and input policy — 18 November 2026

## Reproduced defect

The baseline is commit `aff3059beed9efbfbfcaf6391db1e1df1bb6afdb`.
Its signer imported `nacl.exceptions.BadSignature`, but the supported PyNaCl
API exports `BadSignatureError`. The resulting `ImportError` silently selected
the cryptography fallback even with PyNaCl installed. This was reproduced with
PyNaCl 1.6.2 and cryptography 50.0.0; PyNaCl 1.5.0 also exports the correct
exception name.

With that baseline fallback, a supplied compressed identity public key,
signature point R equal to the identity, and scalar S equal to zero passed
signature verification without knowledge of a private signing key. Replacing
the public key and all six signatures in a temporary copy of the existing
synthetic signed-log fixture produced an overall local PASS: the unchanged
event hashes, attempt/outcome relationships and Merkle root still passed.
The original fixture was not modified. This is a reproduced verifier defect,
not evidence that a deployed application has been exploited.

## Repair and compatibility

- Import and catch `BadSignatureError`, so an installed PyNaCl backend is
  actually selected. Preserve the documented cryptography fallback.
- Before either backend, require a 32-byte public key and 64-byte signature.
- Require canonical compressed point encodings for the public key and R:
  y must be below 2^255 − 19, and x = 0 cannot carry a set sign bit.
- Reject all eight small-order public keys and R points. Five y coordinates
  cover these eight points; both sign encodings are considered.
- Require S to be less than the Ed25519 subgroup order. S = 0 is not rejected
  solely for being zero; the point policy and signature equation still apply.

This shared input policy runs through instance verification, public-key
verification, their Base64 wrappers, and the CLI/report chain verification
path. Valid signature generation, signed event serialization, event hashing,
Merkle construction, and existing fixture bytes remain unchanged.

The canonical encoding and scalar bounds follow
[RFC 8032 sections 5.1.3 and 5.1.7](https://www.rfc-editor.org/rfc/rfc8032.html).
Rejecting every small-order A/R point is an **additional local PoC restriction**,
not a claim that RFC 8032 requires this exact policy or that CAP/VAP has adopted
it. Curve decoding and signature-equation checks stay in PyNaCl/cryptography.
This small-order filter is not a complete prime-subgroup membership test and
does not claim that the two libraries accept exactly the same inputs in every
other edge case. No new elliptic-curve arithmetic is used in production.

The Base64 transport contract is unchanged. The existing file loader and chain
verifier retain their strict representation checks. Key ownership, producer
identity and external commitments still require independently authenticated
trust material; replacing a file-declared key is not made trustworthy by a
passing local verification result.

## Regression evidence and reproduction

`tests/test_ed25519_policy.py` explicitly loads both real backend paths, rather
than merely setting a Boolean after imports. A missing or incorrectly selected
PyNaCl backend fails the tests; it is not silently skipped.

The 145 focused cases cover the RFC 8032 section 7.1 test-1 signing and
verification vector, changed message/key controls, all eight small-order
points as A and R, all 40 representable noncanonical coordinate/sign encodings,
scalar boundaries, malformed input shapes, and the actual CLI in fresh
processes. Independent test-only decoding/doubling verifies eight distinct
points killed by multiplication by eight. Each backend accepts the unchanged
historical signed log and rejects the identity-key forgery through both
`verify` and `report`; the forged log's hash/Merkle/completeness checks remain
valid, isolating the signature failure.

```sh
python -m pip install -e '.[dev]'
python -m pytest tests/test_ed25519_policy.py -v
python -m pytest tests -v
```

The focused 145 cases and full 412-test suite passed locally with Python 3.12,
PyNaCl 1.6.2 and cryptography 50.0.0. The existing CI now includes these cases in its focused
regression job as well as its full-suite job, and packages this document with
the reviewed source and dependency inventory. Hosted results are recorded on
the repair PR; this preparation note does not assert a deployment outcome.
